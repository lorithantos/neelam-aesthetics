# Work in progress — handover

Status of the campaign-safety work as of 2026-10-03, for whoever picks it up next. The README
describes the design; this file covers where things stand, what was decided and by whom, and
what is still open. Delete it once the open items have homes elsewhere.

- **Branch:** `main`. This is a single-person repo: work is integrated on `main` locally and pushed, with no PRs (owner, 2026-10-03). The old `claude/email-campaign-safety-system-lr7q1m` branch was fast-forwarded into `main`.

## Background

Neelam Aesthetics sends marketing email through **Square Marketing**, which has no API for
campaigns. The one-year / "Beauty Bank" email went out **twice** with mistakes:

1. **First send:** both membership offers were identical.
2. **Second send:** one offer's contents were updated, but both were still "Platinum Member"
   ("Option 1 Platinum Member" and "Option 2 Platinum Member").

The original also had wording errors ("50% Complimentary Wellness Injections", "Hi Beautiful🤍",
the same sentence three times, no join link, no terms). Both sends are reproduced as fixtures
in `tests/Neelam.Campaigns.Tests/SampleCampaigns.cs`, and the README's "Why" table maps each
mistake to the check that now stops it. **Since 2026-10-09 both samples say what was sent**
(`BeautyBankEmail.FirstSend()` / `SecondSend()`, checked word for word): subjects "Celebrate 1
year of Neelam Aesthetics!" and "Celebrate 1 year of Neelam Aesthetics! - Correction" ("WE'RE
TURNING ONE!" is the headline of both); the second send's "Introducing:" offer name, "small Family
business", options "Option 1/2 Platinum Member", option 1's last line entered as sent (Percent off
an item, 50, "Wellness Injection", which ones "Complimentary", per visit: "50% off Complimentary
Wellness Injections per visit") and option 2's "Wellness Injection" and "during visit". So the
second send's names are no longer a Must fix (`tier-names-unique` needs identical names) but
`tier-rung-repeated`, Worth a look; it is still blocked by `terms-required` and
`medical-disclaimer`. Whether any instant rule should catch "50% off Complimentary" is open; it is
the proofread's line. The corrected sample is unchanged.

The owner's stated goals: no duplicate offers, and no embarrassing mistakes "that a simple LLM
could catch".

## Decided by the owner

Treat these as fixed unless the owner reopens them.

- The sending platform is **Square Marketing**, not Squarespace.
- The stack is **ASP.NET / Blazor Server on Azure App Service**.
- Storage is **Azure Storage only**, with no SQL or other database. Extended on 2026-10-03: **Table Storage** in the same account holds metadata (clients, support grants, approvals, the activity trail and known items; dismissals are planned there but not built), reached with the managed identity like the blobs. Saves are never indexed there.
- Infrastructure is written in **Bicep**.
- **Managed identity only.** No account keys, SAS or client secrets, anywhere; the resource group denies key authentication through Azure Policy (see `infra/main.bicep`). Only the server matters; local runs need not prove it.
- **Connection strings: fine, but never in GitHub** (2026-10-02, replacing 2026-10-01's "no connection strings at all"). The Application Insights connection string is acceptable. The general case is not a concern; a connection string just has to be stored where it would not be expected to be passed on, such as an App Service setting, and must not appear in any GitHub data. `CredentialGuard` now refuses only secrets (keys, SAS, passwords); `RepositoryTests` scans every file git would commit for a real-looking key. Git history was checked by hand on 2026-10-02 and holds only placeholders.
- **Saves are date/time-stamped blobs.** Any blob can be deleted with no remaining record, so there is no index, versioning, soft delete or logging that would keep one. Clarified on 2026-10-02: the rule is about not keeping blob history, so a deleted save's contents cannot be recovered. Telemetry that names a blob is fine, because it never holds the blob's data, and customer data does not live in blob names or metadata. **Refined by the owner on 2026-10-09:** "We want as much tracking as we can - deletions too are recorded, but not the data." A deleted save's *contents* stay unrecoverable (no versioning, soft delete, change feed or storage logs), but an activity event saying that save X of campaign Y was deleted at time T, with no subject, text or label, is wanted. See "Approvals and the activity trail" below.
- **Undo is forgiving for a day** (owner, 2026-10-09). "Undo last save" sits right under Save, so one misclick deleted a campaign with a single save for good. Undo now marks the save instead: the time it was undone goes in that blob's own metadata (`undone`), with no index or list of undone saves, and every list, history, opening, check and preview leaves it out, so to the client it is gone at once. For the grace period the editor offers **Restore**, which clears the mark, also after leaving the page and coming back (a campaign or template whose every save was undone shows a Restore page at its address). Leaving the page deletes nothing. A background sweep (`UndoSweep`, at startup and then every `Undo:SweepInterval`, hourly) lists each client's blobs, reads the marks, and deletes every save undone longer ago than the grace period; it keeps no state, so a crash part-way is finished by the next run. Hardened after review (2026-10-09): the sweep covers every client in the clients table and, in Prototype mode, `Prototype:Client` too, once, even with no row for it or an unreadable table; each delete is conditional on the blob's ETag as listed (`IBlobBackend.DeleteIfUnchangedAsync`, If-Match), so a save restored between listing and delete survives; one client failing never stops the others. The period is configuration, `Undo:GracePeriod` = `1.00:00:00` in `appsettings.json`, required (the app refuses to start without a positive one); `Undo:SweepInterval` must lie between a millisecond and 49 days, the range its timer can wait, or the app refuses to start. **This is a deliberate, bounded exception to "a deleted save leaves no record":** for the grace period an undone save still exists. Once the sweep has deleted it, nothing of its contents remains, exactly as before; blob soft delete, versioning and change feed stay off. (Since the activity trail, 2026-10-09, a `DeletedBySweep` event and any approval row for that save stay, by id only, and `infra/main.bicep` gained the `activity` and `knownItems` tables; neither holds content.) Undo applies to drafts and templates (`DraftSession`, `TemplateSession`); a client's catalog and policy (`DocumentStore`) have no undo page yet and still delete outright; her look has had one since 2026-10-09 (see "Client look"), and the sweep covers it.
- **Clients and access** (2026-10-03; the README's "Clients and access" section is the design):
  - One deployment serves every client. The tool is for people who cannot set this up themselves, so the operator onboards and runs each client; clients' people only sign in.
  - Separation between clients is enforced **in code**, from Entra alone (owner, 2026-10-03: "everything should be Entra based"). Each client has an Entra security group the operator manages, and the sign-in token says which groups a user is in. **Operator** is an app role, which the operator can give to anyone helping them, with the same limits. No membership or role lives in a table or a setting. This replaces the per-deployment `Storage:Client` / `clientName` from commit `7141d54`, which the rework removes.
  - One container per client, named by `ClientName`, with the same layout for every client.
  - The operator role covers clients, members and settings, **not** campaign data. Reading a client's drafts and templates takes a **support grant, which the client grants** in the app, with a reason and an expiry. The row stays as the record.
  - **Exception until 1.0:** the operator works with Neelam's data directly while the tool is shaped with Neelam. This is a standing support grant marked until 1.0, removed at 1.0.
  - **The catalog is the client's:** the procedures and medications to offer, and their prices, live in the client's own container (`{client}/catalog/{stamp}.json`). The operator does not need them, and sees them only under a support grant (refined 2026-10-03).
  - **Check policy is the client's too:** restricted terms, medical terms and the emoji limit are client decisions. Each client sees and controls its own policy, at `{client}/policy/{stamp}.json` in its own container, loosening included. The operator sees it only under a grant (decided 2026-10-03).
  - **Each client has its own look**, at `settings/{client}/{stamp}.json` in a `settings` container. That client's members and the operator can both read and edit it; other clients cannot see it. Timestamped like saves.
  - **Development** runs against a separate test deployment with no client data; production drops `developerPrincipalId`. Done 2026-10-08 (owner's call): `infra/test.bicepparam` names the developer, who gets Blob and Table Data Contributor on the whole test account; the template honours it only when `environmentName` is `Test`, and `InfrastructureTests` pins both.
- **Security is declared now and enforced at rollout** (2026-10-03). Every page and endpoint carries its real `[Authorize(Policy = ...)]` attribute from the start, and a contract test fails the build if one is missing. While prototyping, the policies are registered permissively in one place; at rollout (before 1.0) that one registration changes to "signed in and holding the Entra app role", and every attribute takes effect at once. This keeps the Entra setup (app registration, app roles, client groups) from blocking all other work. Two conditions: the **tests run with the enforcing policies from day one**, so the attributes are proven continuously; and permissive mode runs only where there is **no real client data** (local, and the test deployment), never on a deployment holding Neelam's data.
- Campaigns are created **from templates**. Refined 2026-10-03 under the owner's principle **"data over dogma"**: the campaign model is hard-coded to Neelam's membership email (fixed sections; one `Offer` of `Tier`s with `MonthlyPrice`; Beauty Bank's benefit kinds), so templates are to define structure as ordered **blocks**, with rules attached to block types and the typed tiered offer kept as one block type. The block vocabulary is to be derived from real client emails, not an assumed list. Decided the same day: no older campaigns exist yet, so it is **best effort from a sample of one** (the Beauty Bank email), refined as examples arrive. **Templates are the client's own data**, in its container: clients can build their own (with the ability, if not yet the competence), and the operator does **breakdowns on request**, under the client's support grant. Built the same day; one judgment call made with it, the owner's to overrule: "an email needs a button" (`cta-required`) now applies only to an email with an offer, which was the Beauty Bank failure; other templates mark their buttons required or not.
- **Tier copy must not merely copy everything.** It marks copied benefits unreviewed. **Since 2026-10-09 (owner) it keeps the name and the price**, replacing "leaves them blank": changing either tier is easier than being made to invent a name or price, which could push her into reordering tiers. The rules are the safety net: while the tiers share a name (`tier-names-unique`) or the copy costs the same as the tier before it (`tier-prices-increase`) it is a Must fix, which blocks approval and export; both messages are neutral about which tier to change ("Rename either one.", "Tier 2 costs the same as tier 1; change either price."; since 2026-10-09 prices may run either way, see "Tier order" under "Tier-name ladders").
- An **AI proofread** is part of the gate.
- **"Worth a look" is shown at export, and never blocks** (owner, 2026-10-09; answers the "acknowledged individually" half of open decision 3: no). First: "We should pop up a list of warnings when exporting without explicitly addressing items like '110% off of botox'." Then, correcting a first build that required each warning to be acknowledged: "This is handholding, not handcuffs." Built the same day:
  - **At export**, an approved version (nothing to fix, unchanged since) whose "Worth a look" findings nobody has been shown at export gets, in place of the copy blocks and the JSON download, a list headed "Before you copy it into Square": "N things are worth a look. None of them stops the email. If one is a mistake, go to it and fix it; if it is right as written, carry on." Every warning is listed with its place as a link to that field's block on the page (the subject line to the subject; "Whole email" has no link). One button, **Export anyway**, goes on; there is no per-item acknowledgement. Under it: "Fixing one changes the campaign: save it again and approve the new version." and (since the keys, below) "You won't be asked again about these for this campaign, in this version or a later one, while they read the same; only something new would come up. The export notes that you saw them and went on." (said "for this version" until they carried across saves, below)
  - **Once per version.** Going on is recorded with that save's approval, so the list is not shown again for it, by anyone. A new save is a new version and shows it again once approved; a label-only save carries the approval and this with it (`KeepApprovalAsync`); withdrawing the approval or undoing the save leaves it behind, so approving again shows the list again. *(Superseded the same day, below: new warnings on the same version are shown, and what was seen carries across saves.)*
  - **Warnings she has not seen come back** (owner's approval, 2026-10-09, replacing the judgment call that new warnings on the same version are not shown again). Going on records, beside who and when, which warnings had been shown: one key per finding (`Finding.SeenKey`: the first 32 hex digits of SHA-256 over its rule, place and message, so hashes only, never a finding's text), comma-separated in a `WarningsSeen` column on the same approvals row (no infra change). Keys add up: going on again adds the new ones and records who and when anew. `ReviewReport.UnseenWarnings` is every warning whose key is not recorded; `WarningsToSee` and `CanExport` use it, so it is the same gate as before, no second path. On a later visit, if any current warning is new (her known items, registered numbers or a check's data changed), the list comes back with only the new ones: "1 new thing is worth a look since you last exported." (or "N new things are"), the same jump links and Export anyway; warnings that went away need nothing, and one she was shown stays shown while it reads the same (a changed message is a new key). A row from before keys were kept has no column: every current warning counts as unseen, so the list shows once more, and going on then records the keys. The JSON's `worthALookSeen` stays {by, at}, now of the latest going on. The page checks and records with the same business it exports with (`Business`, with her library and ladders; the list used to be checked with `_business` alone).
  - **What was seen carries across saves** (owner, 2026-10-09: "yes, carry across saves"; a staging check had shown that after Export anyway on one version, adding a tier and approving again listed the old, unchanged warning beside the new one). A key recorded on any approvals row of the campaign counts as seen on every save of it: an unchanged warning (same rule, place and wording) is not listed on a later version, and once that version is approved with nothing new the export is simply there; a warning the new save adds, or rewords (a new key), is listed alone, as new ("1 new thing is worth a look since you last exported." / "N new things are"). **Where:** nothing moves; the keys stay on the rows they were recorded on, and the store reads the union across the campaign's rows (`ApprovalRecord.SeenAcross`, used by `CampaignStore.HistoryAsync`, `ApproveAsync`, `KeepApprovalAsync` and `WarningsSeenAtExportAsync`), so the approval a save carries has the campaign's record. Going on writes only to the exported save's row (its own keys plus those shown); a save approved with nothing new gets no record of its own. **Withdrawn approvals and undone or deleted saves still count:** their rows stay (as before), and she was shown what they record; approving a save again after a withdrawal keeps what its row recorded rather than replacing it with a bare approval. Another campaign's rows never count. **The gate is unchanged:** `CanExport` still needs every current warning's key seen, from the same report. **The JSON's `worthALookSeen`** is {by, at} of the latest going on for the campaign, on this version or an earlier one; so on a version approved with nothing new it names the earlier going on (schema description and `ExportedReview` say so; `Problems` unchanged, since it is still present exactly when there are worthALook items). Rows from before keys were kept still show the list once more (keys null only when no row of the campaign has any).
  - **Who and when:** in Prototype the name typed for that version's approval, as approvals are recorded (nobody signs in); signed in, the sign-in's name. UTC, from `TimeProvider`.
  - **The gate:** one mechanism, in `ReviewReport`: `CanExport` now also needs every warning seen (`WarningsSeen`, set only by `CampaignGate`, from the approval on the demo path, `DemoReview`, and from a `warningsSeen` argument in Enforced, `ReviewAsync`). `WarningsToSee` says the list is what stands in the way. So `EditorExport.Blocks` and `AssistantExport.Build` both refuse the same report, with "Campaign has N thing(s) worth a look that nobody has been shown at export yet." The existing `Dismissal` (an AI blocker turned into a warning by a named person) is unchanged and is per finding; it was not reused, since the owner wants no per-item step. **Must fix is unchanged:** it still blocks approval and export, is never in the list, and going on never passes it.
  - **Stored** on the save's row in the existing `approvals` table, columns `WarningsSeenBy` and `WarningsSeenAt` (left out until then), and since the keys `WarningsSeen`: no new table and no infra change. Never what the findings said; which ones only as hashes. Activity: `WarningsSeenAtExport` on the campaign and save, by id. ## Block catalog (owner's decision, 2026-10-09; built the same day)

**Decided by the owner:** "Let's change the way these are created into json templates that are read in. This will allow more customization of template structures." Block definitions and the lines under "What the checks look for in this block" were C# (`BlockGuide.All`), with one hand-written prose list shared by every text block, so the Fine print block told her both "Any text here counts as the disclaimer a medical term needs." and "A medical term needs a disclaimer in a fine-print block." (she found it on her phone). House rule 3 in `JanetHome/notes/csharp-house-rules.md` came from this.

- **The files:** `src/Neelam.Campaigns/Catalog/blocks.json` and `Catalog/rules.json`, content of the domain project, which the block types and checks they describe live in. They are copied under `Catalog/` into the output of every project that references it: the web app (and its `dotnet publish`, by `CopyToPublishDirectory`) and the tests. That publish carries them is MSBuild's standard handling of a referenced project's content and has not been run here (no Janet tool publishes); check the package once, or the deployed app, which would not start without them.
  - `blocks.json`: `{ "blocks": [ { "type", "label", "description", "rules": [rule ids], "wording": [ { "rules": [...], "says" } ] } ] }`, one entry per `BlockType`, in the order the editor's "Add a block" list shows them. `type` is the enum's name (`FinePrint`). `rules` are the rule ids the checks bring to the block, in the order their lines show. `wording` is optional: the block's own words for some of its rules, said once where the first of them stands, in place of their lines from `rules.json`.
  - `rules.json`: `{ "rules": [ { "id", "description" } or { "id", "describedWith" } ] }`, one entry per rule id the checks report. A rule `describedWith` another shares that rule's line, so one line can cover several rules without its words being written twice (`emoji-spacing` and `emoji-budget` are one line; the tier names, distinct benefits, price order and price-given rules are one).
- **Where a rule is worded per block (said here, as asked):** three blocks word rules their own way. Button: `cta-required` reads "An email with an offer needs one." (the Offer's line, "It needs a button somewhere in the email...", is the description). Image: one line for all five text rules, "Its description ... gets the text checks." Fine print: `medical-disclaimer` reads "Any text here counts as the disclaimer a medical term needs." So the Fine print block still names that rule, since its line is about it, and no longer shows the general "A medical term needs a disclaimer in a fine-print block." Every other block's guide reads word for word as before (a test holds each to a snapshot taken from the old code, `tests/Neelam.Campaigns.Tests/block-guides-before.json`); the Fine print block's rule list is the same rules, `medical-disclaimer` now first so its line shows first.
- **Two rules no block names:** `known-item` and `phone-registered` are reported but are about her registration, not a block, so no block lists them; `rules.json` describes them anyway (the startup check wants every reported rule described), in words not shown anywhere yet.
- **Read once, at startup, and refused when wrong:** `BlockCatalog.Shipped`, called in `Program.cs` and registered as a singleton. Parsed with System.Text.Json (unknown properties refused, so a misspelt name is not ignored); no schema library in the app. The app stops with "The block catalog (Catalog/blocks.json and Catalog/rules.json) does not match the code:" and one line per problem: a block type in code with no entry; an entry for a type the code does not have; a rule id named by a block or described in `rules.json` that no check reports; a reported rule with no description; a duplicate type, rule, or rule within a block; a `describedWith` that names no described rule; wording for a rule the block does not name; no label or description; a file missing or not valid JSON.
- **Which rule ids the checks can report:** `CheckRules.Reported`, a list in code, since the checks are code. A test holds it to the quoted kebab-case ids in `CampaignReview.cs` both ways (the scan the old guide test made), so a new rule in the checks without a line, or a line for a rule that went, fails a test before it can stop the app.
- **Who reads it:** the template editor's block cards and guide and its "Add a block" list (`TemplateEdit`, through `TemplateEditor.Catalog`), new blocks' labels and the "A header block: Give the block a label." error (`TemplateEditor`), the baseline checklist and its order list (`BaselineSection`) and the campaign editor's block names (`CampaignEdit`), each from the injected `BlockCatalog`. `TemplateAdvice`, `TemplateBaseline` and How it works never read the guide. `TemplateEditor` and `TemplateSession` now take the catalog as an argument. Page elements: `block-checks-{index}` (a block's guide) and `add-blocks`.
- **Schemas:** `docs/block-catalog/blocks.schema.json` and `rules.schema.json`, checked by the test project only, as `assistant-export.schema.json` is.
- **To add a rule:** add its checks in `CampaignReview` reporting a new id, add the id to `CheckRules.Reported`, give it a line in `rules.json` (or `describedWith` a rule whose line covers it), and name it in the `rules` of each block in `blocks.json` it applies to. **To reword a line:** edit `rules.json`, or the block's `wording`; no code. **To reorder the Add a block list:** reorder `blocks.json`. **To add a block type:** see "Extending later".
- **The seam for customisation (not built):** one catalog serves every client, the shipped one. A client's own, over an operator standard as the baseline and the ladders do it, would be another `BlockCatalog` from `BlockCatalog.Load(blocksJson, rulesJson, CheckRules.Reported)`, read from the client's container and handed to `TemplateSession`/`TemplateEditor` instead of the shipped one, and to the pages that inject it today.
- **Not moved: the Square widget table.** `SquareWidgets.ByKind` (export block kind to Square widget) stays in `AssistantExport.cs`. It is keyed by the export's `BlockKind`, not `BlockType`, and read by static `AssistantExport.Build`, `Json` and `Problems` (whose own checks use it) and by `CampaignEdit`; moving it to a data file means threading a platform mapping through the export, the gate and their tests, a separate change with its own risk to a schema-pinned export (thread item).

### Extending later

The owner, 2026-10-09: "We don't want her to have to write code, but we want this to be something we can resurface later - say we need a different block type because we are supporting some wix platform or whatever crm." Nothing below is built.

- **A new block type, today:** the catalog entry is data, but the type itself is code: a `BlockType` value, its content record (`TemplateBlock` fixed content and the campaign's block), its fields in the template and campaign editors, its text for the checks (`CampaignText`), its JSON (`CampaignJson`), and its export kind (`EditorExport`, `BlockKind`, and the Square widget row). A block made only of shapes that exist (a second text block that differs from Paragraphs in name and purpose alone) would still need that code today, since every type is an enum value with its own editor case; making such a block pure data would mean a generic "text block" type whose label and purpose come from the catalog, a design call for the owner. A new field shape (a date range, a price list) always needs code: the shape and what it guarantees are what code keeps.
- **A second sending platform (Wix, another CRM):** a mapping of the export's block kinds to that platform's widgets, as `SquareWidgets.ByKind` is for Square (best as a data file per platform, such as `platforms/square.json`, once that table moves), plus that platform's fill-in and verify instructions for the assistant export (today fixed text for Square in `AssistantExport`), and a way to choose the platform per client. The block catalog says nothing about any platform, so it would not change.

  same way. A row from another client's partition is still refused

  rest of the page; the workspace behaviour is tested. Other pages that read the clients table

  presidential." So:

    words only: a near miss of a line's pattern (same kind) suggests that line at the amounts written

  - **Reading a page:** `RenderedPage.Named(page, name)` (`tests/Neelam.Campaigns.Tests/RenderedPage.cs`) returns that element's text and fails unless exactly one element has the name. A check that something is nowhere on the page uses `RenderedPage.Text(page)` (what a reader sees: no comments, scripts, tags or attributes) or `RenderedPage.Links(page)`, never the raw HTML.
  - **Older whole-page checks** still search raw HTML; each is safe only because base64 cannot hold its needle: it has a character outside letters, digits and `+/=-_` (a space, `<`, `.`), or is seven or more characters (a chance match is then under one in a hundred million per page). Convert them to named elements when their tests are next touched; any new short one must be named.
