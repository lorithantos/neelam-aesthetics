describes the design; this file covers where things stand, what was decided and by whom, and

## Background

Neelam Aesthetics sends marketing email through **Square Marketing**, which has no API for
campaigns. The one-year / "Beauty Bank" email went out **twice** with mistakes:

1. **First send:** both membership offers were identical.
2. **Second send:** one offer's contents were updated, but both were still "Platinum Member"
   ("Option 1 Platinum Member" and "Option 2 Platinum Member").

The original also had wording errors ("50% Complimentary Wellness Injections", "Hi Beautiful🤍",
the same sentence three times, no join link, no terms). Both sends are reproduced as fixtures
in `tests/Neelam.Campaigns.Tests/SampleCampaigns.cs`, and the README's "Why" table maps each
mistake to the check that now stops it. **Since 2026-10-09 both samples say what was sent**
(`BeautyBankEmail.FirstSend()` / `SecondSend()`, checked word for word): subjects "Celebrate 1
year of Neelam Aesthetics!" and "Celebrate 1 year of Neelam Aesthetics! - Correction" ("WE'RE
TURNING ONE!" is the headline of both); the second send's "Introducing:" offer name, "small Family
business", options "Option 1/2 Platinum Member", option 1's last line entered as sent (Percent off
an item, 50, "Wellness Injection", which ones "Complimentary", per visit: "50% off Complimentary
Wellness Injections per visit") and option 2's "Wellness Injection" and "during visit". So the
second send's names are no longer a Must fix (`tier-names-unique` needs identical names) but
`tier-rung-repeated`, Worth a look; it is still blocked by `terms-required` and
`medical-disclaimer`. Whether any instant rule should catch "50% off Complimentary" is open; it is
the proofread's line. The corrected sample is unchanged.

The owner's stated goals: no duplicate offers, and no embarrassing mistakes "that a simple LLM
could catch".

## Decided by the owner

Treat these as fixed unless the owner reopens them.

- The sending platform is **Square Marketing**, not Squarespace.
- The stack is **ASP.NET / Blazor Server on Azure App Service**.
- Storage is **Azure Storage only**, with no SQL or other database. Extended on 2026-10-03: **Table Storage** in the same account holds metadata (clients, support grants, approvals, the activity trail and known items; dismissals are planned there but not built), reached with the managed identity like the blobs. Saves are never indexed there.
- Infrastructure is written in **Bicep**.
- **Managed identity only.** No account keys, SAS or client secrets, anywhere; the resource group denies key authentication through Azure Policy (see `infra/main.bicep`). Only the server matters; local runs need not prove it. **One exception, the owner's (2026-10-09):** the LLM proofread's Anthropic API key ("For now I will donate my credits"), in Key Vault and allowed by `CredentialGuard` in `Proofread:AnthropicApiKey` alone; see "LLM proofread" below.
- **Connection strings: fine, but never in GitHub** (2026-10-02, replacing 2026-10-01's "no connection strings at all"). The Application Insights connection string is acceptable. The general case is not a concern; a connection string just has to be stored where it would not be expected to be passed on, such as an App Service setting, and must not appear in any GitHub data. `CredentialGuard` now refuses only secrets (keys, SAS, passwords); `RepositoryTests` scans every file git would commit for a real-looking key. Git history was checked by hand on 2026-10-02 and holds only placeholders.
- **Saves are date/time-stamped blobs.** Any blob can be deleted with no remaining record, so there is no index, versioning, soft delete or logging that would keep one. Clarified on 2026-10-02: the rule is about not keeping blob history, so a deleted save's contents cannot be recovered. Telemetry that names a blob is fine, because it never holds the blob's data, and customer data does not live in blob names or metadata. **Refined by the owner on 2026-10-09:** "We want as much tracking as we can - deletions too are recorded, but not the data." A deleted save's *contents* stay unrecoverable (no versioning, soft delete, change feed or storage logs), but an activity event saying that save X of campaign Y was deleted at time T, with no subject, text or label, is wanted. See "Approvals and the activity trail" below.
- **Undo is forgiving for a day** (owner, 2026-10-09). "Undo last save" sits right under Save, so one misclick deleted a campaign with a single save for good. Undo now marks the save instead: the time it was undone goes in that blob's own metadata (`undone`), with no index or list of undone saves, and every list, history, opening, check and preview leaves it out, so to the client it is gone at once. For the grace period the editor offers **Restore**, which clears the mark, also after leaving the page and coming back (a campaign or template whose every save was undone shows a Restore page at its address). Leaving the page deletes nothing. A background sweep (`UndoSweep`, at startup and then every `Undo:SweepInterval`, hourly) lists each client's blobs, reads the marks, and deletes every save undone longer ago than the grace period; it keeps no state, so a crash part-way is finished by the next run. Hardened after review (2026-10-09): the sweep covers every client in the clients table and, in Prototype mode, `Prototype:Client` too, once, even with no row for it or an unreadable table; each delete is conditional on the blob's ETag as listed (`IBlobBackend.DeleteIfUnchangedAsync`, If-Match), so a save restored between listing and delete survives; one client failing never stops the others. The period is configuration, `Undo:GracePeriod` = `1.00:00:00` in `appsettings.json`, required (the app refuses to start without a positive one); **since 2026-11-03 (owner: "set as 90 days, and one hour") it must also lie between `Undo:GracePeriodMinimum` (`01:00:00`) and `Undo:GracePeriodMaximum` (`90.00:00:00`)**, both in `appsettings.json` and the same as the code's defaults, or the app refuses to start, as for `CampaignWatch:Interval`; no test lowers the minimum (owner: "the tests shouldn't need any smaller limits as they should not be using a real clock"): tests keep a period inside the limits and move a fake clock past it; **periods are said in words by one function, `TimeWords.Period`** (owner, 2026-11-03), everywhere a period is shown: a whole number of the biggest unit it holds, or of the unit below (weeks to days, days to hours), is said so ("2 weeks", "30 days", "36 hours", "a day", "365 days"); otherwise the biggest unit's wholes, rounded down, with a "+" ("4 weeks+" for 29.5 days, "1 day+" for 25.5 hours, "1 hour+" for 90 minutes, "57 weeks+" for 400.5 days); no months or years. Two readings of the owner's examples, the owner's to overrule: hours never go down to minutes ("90 minutes" fits minutes exactly, yet the owner's example reads "1 hour+", while "36 hours" and "30 days" go one unit down), and below a minute it is seconds the same way ("30 seconds", "a second", "1 second+"; "less than a second" below that), since the warm-up page's retry and the starts page's thresholds are in seconds. The template page had its own wording ("24 hours"); it now says "a day" like the rest; `Undo:SweepInterval` must lie between a millisecond and 49 days, the range its timer can wait, or the app refuses to start. **This is a deliberate, bounded exception to "a deleted save leaves no record":** for the grace period an undone save still exists. Once the sweep has deleted it, nothing of its contents remains, exactly as before; blob soft delete, versioning and change feed stay off. (Since the activity trail, 2026-10-09, a `DeletedBySweep` event and any approval row for that save stay, by id only, and `infra/main.bicep` gained the `activity` and `knownItems` tables; neither holds content.) Undo applies to drafts and templates (`DraftSession`, `TemplateSession`); a client's catalog and policy (`DocumentStore`) have no undo page yet and still delete outright; her look has had one since 2026-10-09 (see "Client look"), and the sweep covers it.

## Block catalog (owner's decision, 2026-10-09; built the same day)

**Decided by the owner:** "Let's change the way these are created into json templates that are read in. This will allow more customization of template structures." Block definitions and the lines under "What the checks look for in this block" were C# (`BlockGuide.All`), with one hand-written prose list shared by every text block, so the Fine print block told her both "Any text here counts as the disclaimer a medical term needs." and "A medical term needs a disclaimer in a fine-print block." (she found it on her phone). House rule 3 in `JanetHome/notes/csharp-house-rules.md` came from this.

- **The files:** `src/Neelam.Campaigns/Catalog/blocks.json` and `Catalog/rules.json`, content of the domain project, which the block types and checks they describe live in. They are copied under `Catalog/` into the output of every project that references it: the web app (and its `dotnet publish`, by `CopyToPublishDirectory`) and the tests. That publish carries them is MSBuild's standard handling of a referenced project's content and has not been run here (no Janet tool publishes); check the package once, or the deployed app, which would not start without them.
  - `blocks.json`: `{ "blocks": [ { "type", "label", "description", "rules": [rule ids], "wording": [ { "rules": [...], "says" } ] } ] }`, one entry per `BlockType`, in the order the editor's "Add a block" list shows them. `type` is the enum's name (`FinePrint`). `rules` are the rule ids the checks bring to the block, in the order their lines show. `wording` is optional: the block's own words for some of its rules, said once where the first of them stands, in place of their lines from `rules.json`.
  - `rules.json`: `{ "rules": [ { "id", "description" } or { "id", "describedWith" } ] }`, one entry per rule id the checks report. A rule `describedWith` another shares that rule's line, so one line can cover several rules without its words being written twice (`emoji-spacing` and `emoji-budget` are one line; the tier names, distinct benefits, price order and price-given rules are one).
- **Where a rule is worded per block (said here, as asked):** three blocks word rules their own way. Button: `cta-required` reads "An email with an offer needs one." (the Offer's line, "It needs a button somewhere in the email...", is the description). Image: one line for all five text rules, "Its description ... gets the text checks." Fine print: `medical-disclaimer` reads "Any text here counts as the disclaimer a medical term needs." So the Fine print block still names that rule, since its line is about it, and no longer shows the general "A medical term needs a disclaimer in a fine-print block." Every other block's guide reads word for word as before (a test holds each to a snapshot taken from the old code, `tests/Neelam.Campaigns.Tests/block-guides-before.json`); the Fine print block's rule list is the same rules, `medical-disclaimer` now first so its line shows first.
- **Two rules no block names:** `known-item` and `phone-registered` are reported but are about her registration, not a block, so no block lists them; `rules.json` describes them anyway (the startup check wants every reported rule described), in words not shown anywhere yet.
- **Read once, at startup, and refused when wrong:** `BlockCatalog.Shipped`, called in `Program.cs` and registered as a singleton. Parsed with System.Text.Json (unknown properties refused, so a misspelt name is not ignored); no schema library in the app. The app stops with "The block catalog (Catalog/blocks.json and Catalog/rules.json) does not match the code:" and one line per problem: a block type in code with no entry; an entry for a type the code does not have; a rule id named by a block or described in `rules.json` that no check reports; a reported rule with no description; a duplicate type, rule, or rule within a block; a `describedWith` that names no described rule; wording for a rule the block does not name; no label or description; a file missing or not valid JSON.
- **Which rule ids the checks can report:** `CheckRules.Reported`, a list in code, since the checks are code. A test holds it to the quoted kebab-case ids in `CampaignReview.cs` both ways (the scan the old guide test made), so a new rule in the checks without a line, or a line for a rule that went, fails a test before it can stop the app.
- **Who reads it:** the template editor's block cards and guide and its "Add a block" list (`TemplateEdit`, through `TemplateEditor.Catalog`), new blocks' labels and the "A header block: Give the block a label." error (`TemplateEditor`), the baseline checklist and its order list (`BaselineSection`) and the campaign editor's block names (`CampaignEdit`), each from the injected `BlockCatalog`. `TemplateAdvice`, `TemplateBaseline` and How it works never read the guide. `TemplateEditor` and `TemplateSession` now take the catalog as an argument. Page elements: `block-checks-{index}` (a block's guide) and `add-blocks`.
- **Schemas:** `docs/block-catalog/blocks.schema.json` and `rules.schema.json`, checked by the test project only, as `assistant-export.schema.json` is.
- **To add a rule:** add its checks in `CampaignReview` reporting a new id, add the id to `CheckRules.Reported`, give it a line in `rules.json` (or `describedWith` a rule whose line covers it), and name it in the `rules` of each block in `blocks.json` it applies to. **To reword a line:** edit `rules.json`, or the block's `wording`; no code. **To reorder the Add a block list:** reorder `blocks.json`. **To add a block type:** see "Extending later".
- **The seam for customisation (not built):** one catalog serves every client, the shipped one. A client's own, over an operator standard as the baseline and the ladders do it, would be another `BlockCatalog` from `BlockCatalog.Load(blocksJson, rulesJson, CheckRules.Reported)`, read from the client's container and handed to `TemplateSession`/`TemplateEditor` instead of the shipped one, and to the pages that inject it today.

It is keyed by the export's `BlockKind`, not `BlockType`, and read by static `AssistantExport.Build`, `Json` and `Problems` (whose own checks use it) and by `CampaignEdit`; moving it to a data file means threading a platform mapping through the export, the gate and their tests, a separate change with its own risk to a schema-pinned export (thread item).

### Extending later

The owner, 2026-10-09: "We don't want her to have to write code, but we want this to be something we can resurface later - say we need a different block type because we are supporting some wix platform or whatever crm." Nothing below is built.

- **A new block type, today:** the catalog entry is data, but the type itself is code: a `BlockType` value, its content record (`TemplateBlock` fixed content and the campaign's block), its fields in the template and campaign editors, its text for the checks (`CampaignText`), its JSON (`CampaignJson`), and its export kind (`EditorExport`, `BlockKind`, and the Square widget row). A block made only of shapes that exist (a second text block that differs from Paragraphs in name and purpose alone) would still need that code today, since every type is an enum value with its own editor case; making such a block pure data would mean a generic "text block" type whose label and purpose come from the catalog, a design call for the owner. A new field shape (a date range, a price list) always needs code: the shape and what it guarantees are what code keeps.
- **A second sending platform (Wix, another CRM):** a mapping of the export's block kinds to that platform's widgets, as `SquareWidgets.ByKind` is for Square (best as a data file per platform, such as `platforms/square.json`, once that table moves), plus that platform's fill-in and verify instructions for the assistant export (today fixed text for Square in `AssistantExport`), and a way to choose the platform per client. The block catalog says nothing about any platform, so it would not change.

## Template baseline (owner's decision, 2026-10-09; built the same day)

The parts every template should have, as an ordered list of block types held as data (`TemplateBaseline`): which parts, and the order a new template starts with them in.

- **Decided by the owner:** the operator provides a standard baseline; each client may save its own, which replaces the standard for that client. Deleting its own ("Use the standard baseline") makes the standard apply again; saving an empty one is the only way a client has no baseline. *(Since phase 2 of concurrent edits, 2026-10-11, "Use the standard baseline" saves a version saying the standard applies instead of deleting hers, so a version saved in another tab is never deleted unseen; the owner may overrule, see "Concurrent edits".)* In UI text it is "the standard baseline", never Neelam's: Neelam is a client, not the operator. **A warning, never a block:** a template lacking a part still saves, and the editor lists each missing part ("Your templates usually have a sign-off; this one doesn't."), since a short note such as "we're closed Monday" may rightly have no button. A part counts as present when the template has a block of that type, required or optional (her Membership template's photo is optional, and counts).
- **Evidence for the standard one:** Neelam's five sent emails (Aug-Sep 2026). Every one had a header, a headline, a call-to-action button and a photo; greeting and body text were in four of the five; the latest signs off from the team rather than from one person. So the standard is Header, Heading, Sign-off, Image and Button, in that order, the order her sends put them in (the photo and the button come after the sign-off: the Beauty Bank sends as Square rendered them, `BeautyBankEmail`, and the Membership template deduced from them); greeting and body are not in it. ## Outage signal (owner, 2026-10-10)

**Decided by the owner:** "We can add the measurement to help make certain there are no outages", then, on hearing the cost of the paid test: "yes, heartbeat in and drop the paid test", with the idea "seeing how long it took to serve the request we could know if there was an outage".

- **Built and dropped the same day (3606f4f, removed after it):** an Application Insights standard availability test on the client site's `/healthz`, every 5 minutes from 3 US locations, and a metric alert (2 of 3 locations failing in 5 minutes) emailing an address passed at deploy time (`alertEmail`, never committed). **Why dropped:** about **$13 a month** (25,920 executions at $0.0005, Azure retail prices API, "Standard Web Test Execution", westus3, 2026-10-10) for a site used a few times a month; the owner prefers the in-app record. Nothing of it was ever deployed. **Offered and not chosen:** a log alert on "no requests for N minutes" in Application Insights, about $1.50 a month. Kept from it: `RepositoryTests` scans every committed file for an email address (documentation domains such as example.com excepted), a guard worth having anyway.
- **The heartbeat instead (built the same day):** while the app runs, `Heartbeat` (a hosted service) writes the time about once a minute (`Heartbeat:Interval`, 00:01:00) into the metadata of one blob, `settings/_starts/heartbeat.json` (`alive`, ISO 8601 UTC, and `start`, the start's id; the content is `{}`). Blobs are never overwritten here, but metadata may be, so each beat is one metadata write. Off every request; a failed read or beat is logged by type and the next beat tries again; it stops with the app. **At each start it reads the last heartbeat before its own first beat**, and the start's record keeps `DownFrom` (that heartbeat) and `DownForMs` (start minus it, never below zero), give or take one heartbeat. The record's writer waits up to 30 s for that read before working out "Why". One instance per site: a second instance would beat into the same blob.
- **Why, from the gap (proposed, the owner's to change):** a changed build stamp is "New build"; otherwise under **2 minutes** is "Restart" (a setting changed, a recycle), **2 minutes or more** is "Down for N min" (N s under 2 min, N min under 2 h, then N h M min), and no heartbeat before (the first start ever, or one that could not be read) is "Unknown". The Starts page's **"Down for"** column shows the gap ("Not known" without one) and marks **5 minutes or more** with "Outage", whatever the cause, a new build included. Log line: "Start {StartId}: cause {Cause}; last heartbeat before it {DownFrom}, {DownForMs} ms before the start."
- **What it cannot tell:** a site that stops and never starts again shows nothing until it does start; the gap then says how long. A hung process that still beats is not down by this measure; slow first visits and the getting-ready count are the signs of that. Storage writes about 43,000 a month (pennies), and each beat is a blob dependency in Application Insights, well inside the free 5 GB.

## Time and concurrency in tests: house rule 7, enforced (2026-11-03)

The owner, 2026-11-03: "For coding standards tests must not rely on the system clock" (`note.csharp-house-rules`, Part 1 rule 7). **Enforced since 2026-11-03** by `SystemClockTests.No_test_reads_the_system_clock_or_waits_on_it`, which reads the test assembly's compiled IL (every call, construction and delegate, lambdas and async state machines included) and fails on any use of `DateTime.Now`/`UtcNow`/`Today`, `DateTimeOffset.Now`/`UtcNow`, `TimeProvider.System`, `Thread.Sleep`, `Stopwatch`, `Environment.TickCount`, a `System.Threading.Timer` or `System.Timers.Timer`, `CancellationTokenSource.CancelAfter`, or `Task.Delay`, `PeriodicTimer` or a timed `CancellationTokenSource` not given a `TimeProvider`. Allowed on purpose: a time limit on a wait for a signal (`Task.WaitAsync(TimeSpan)`, 30 s, `Eventually.Patience`), which only fails a test that would otherwise hang.
- **The one fake clock:** `ManualClock` (tests), which replaced both the old `ManualClock` (time only; its timers were the machine's) and `SteppingClock`. Setting `Now` moves the time and fires nothing, so an app's background loops (sweep, heartbeat) stay still while a test moves days; `Advance` moves it and fires every timer then due; its timestamps follow it, so a measured duration is the time moved. `Waiting`, `WaitingFor(dueTime)` and `Fired` let a test see a wait set and prove a move set nothing off. Lock-free (house rule 4).
- **Waits are on signals:** `Pulse` and `Eventually.Until` (re-check on each signal, never on a timer): the held page re-checks on each render, the start records and heartbeat store, loggers, blob deletes, the clients table's reads and the clock each raise one. A wait for something not to happen is replaced by proving the only path to it did not run (no timer fired, a wait set on the clock).
- **Production code that waited on the machine's clock now waits on the app's `TimeProvider`:** the warm-up gate's wait, `/warmup`'s wait, the start record writer's coalesce and its wait for the last heartbeat, the start recording's request timing (`StartLog.Clock`); `Warmup` and `SquarePhotoFetcher` take a required `TimeProvider` (the fetcher's test-only shorter-limit constructor is gone: its test moves the clock past the real ten seconds). Not changed: `TokenPrefetch` still times its one request with a `Stopwatch` (it starts before the host exists; no test needs its time), thread item "Neelam: TokenPrefetch times its request on the machine's clock".

- No test touches the network. Keep it that way, and keep real-service checks as manual probes.
- **A flaky test is a priority-1 fix, never "passed on rerun"** (owner, 2026-10-09: "letting tests go is how we get disasters"). A test that fails and then passes is reported and fixed at its cause before other work, never rerun away, retried or skipped.
- **Page checks name the element they look for** (owner, 2026-10-09: "Checks on pages should know what element they are looking for. These should have individual names that can be located."). Why: every Blazor page carries about 2,000 characters of fresh random base64 (the prerender descriptor and the component state, in HTML comments), so a short string searched over the whole HTML turns up by chance. `Assert.DoesNotContain("PDT", page)` on an Eastern page failed this way: the base64 held "PDT" in 15 of 2,000 requests, so that test, with "EDT" checked the same way on a Pacific page, failed about one run in 70.
  - **Convention:** an element a check reads carries `data-testid`, a kebab-case name unique on its page; an element repeated per item (a card in a list) adds the item's id, as `last-saved-{id}`. The names are for tests and a future browser-driven suite; nothing styles or scripts by them. In use: `site-name` (both layouts), `last-saved` (template and campaign editors), `last-saved-{id}` (the templates and campaigns lists), and the Look page's (listed under "Client look").
  - **Reading a page:** `RenderedPage.Named(page, name)` (`tests/Neelam.Campaigns.Tests/RenderedPage.cs`) returns that element's text and fails unless exactly one element has the name. A check that something is nowhere on the page uses `RenderedPage.Text(page)` (what a reader sees: no comments, scripts, tags or attributes) or `RenderedPage.Links(page)`, never the raw HTML.
  - **Older whole-page checks** still search raw HTML; each is safe only because base64 cannot hold its needle: it has a character outside letters, digits and `+/=-_` (a space, `<`, `.`), or is seven or more characters (a chance match is then under one in a hundred million per page). Convert them to named elements when their tests are next touched; any new short one must be named.
